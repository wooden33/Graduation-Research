# RQ1：CogPath 的程序分析与 Agent 工作流能否提升测试生成效果？

## 研究问题

**RQ1：在相同目标方法、模型和资源预算下，CogPath 的 Constraint-Hints 与 Backward Slicing，以及将 CogPath 分析结果接入 OpenHands 的工具使用工作流，能否比 Panta、HITS 和原始 CogPath 生成更高覆盖率且更可靠的单元测试？这种提升需要多少额外模型调用与运行时间？**

本 RQ 比较测试生成方法和端到端工作流，不预设 agentic 方案一定胜出。论文应检验“分析证据 + 迭代工具执行”是否带来可重复的收益，并同时报告成本、有效测试和故障检测能力；若覆盖收益被额外预算解释，结论应表述为预算换性能，而不是方法本身更有效。

## 比较对象

| 组别 | 方法 | 实验中的操作定义 |
| --- | --- | --- |
| A | **Panta** | 使用 Panta 的可复现实现，按其论文/官方配置运行。它是外部基线；当前 CogPath 仓库只有派生 CSV，没有实现和原始报告。在取得代码、模型配置和运行记录前，不把历史 CSV 纳入本 RQ 的同条件统计。 |
| B | **HITS** | 使用 HITS 的方法切片提示生成测试。记录并修复当前实现中影响实验的已知问题；报告采用的代码版本、切片数量上限、修复策略和模型调用预算。 |
| C | **CogPath** | 使用现有 CogPath 迭代流程，启用 Constraint-Hints 和 Backward Slicing。明确目标路径选择、切片触发时机、每轮生成/修复次数及停止条件。 |
| D | **CogPath + OpenHands** | OpenHands 负责读取隔离项目、规划测试任务、调用 CogPath 提供的目标分支/约束/切片证据、编写测试、执行 Maven 并根据失败反馈修复。CogPath 在这里提供可核验的程序分析工具；OpenHands 的仓库浏览、shell 和文件编辑能力属于该组的工作流处理。 |

**D 组实现边界需要在实验前固定。** 需记录 OpenHands 实际可调用的 CogPath 接口：例如生成目标分支提示和切片结果的 CLI/API，及其输入输出格式。若 OpenHands 只是把 CogPath 报告文本放入 prompt，而不能按需运行分析工具，应将其称为“CogPath 提示 + OpenHands”，不要称为工具增强的 CogPath agent。

## 假设

- **H1（覆盖）**：CogPath + OpenHands 的最终分支覆盖率高于原始 CogPath，并在同预算下高于 HITS 和 Panta。
- **H2（有效性）**：CogPath + OpenHands 生成的测试具有不低于其他方法的编译成功率和测试通过率。
- **H3（效率）**：CogPath 的分析提示能减少 agent 的盲目探索；在达到相近覆盖率时，CogPath + OpenHands 使用的模型 token 或墙钟时间低于不含 CogPath 分析的 agent 工作流。若本 RQ 暂不增加该 agent 对照，则 H3 留作后续研究问题，不从四组结果推断。
- **H4（测试价值）**：CogPath + OpenHands 在变异得分上高于只以覆盖率驱动的方法，或至少不以明显降低变异得分换取覆盖提升。

H1、H2 是本 RQ 的主要检验目标；H3、H4 只有在设置相应对照并完成所需测量后才能作结论。为了判断增益是否来自 agent 本身，后续建议补充一个 **OpenHands vanilla** 组：相同 agent、提示目标、模型和预算，但不提供 CogPath 的约束/切片证据。没有该组时，只能评价完整组合工作流，不能单独归因于 OpenHands 或 CogPath 分析。

## 实验设计

### 案例与运行单位

- 以论文中使用的 Defects4J Java 项目为候选总体，沿用相同的版本和高复杂度方法筛选规则；报告项目、类、方法数量，以及因构建或环境问题排除的样本。
- 四组使用**完全相同的方法清单**。以“目标方法 × 随机重复”为配对区组，让各组面对相同代码、初始测试状态和重复编号。
- 每个方法在独立 subject 副本中运行。原始数据集保持只读；每次运行保存源码/测试前后差异、命令日志、覆盖报告、配置快照和生成测试。
- 先用少量方法验证协议和 runner，再锁定配置扩展样本。完整数据集运行需明确并发数、预算上限和失败重试策略，不能把环境故障当成方法失败。

### 模型与预算

- 主实验统一使用 `deepseek-v4.1-flash` LiteLLM profile，固定温度、最大输出、系统提示、API 端点配置和模型 profile 版本；密钥仅从环境变量读取。
- 固定每个方法每次重复可使用的**墙钟时间上限和总模型 token 上限**，并在超限时停止。统计 token 时包含约束求解、切片生成、agent 规划、测试生成和修复的全部请求；报告每组实际消耗分布。
- 各组按其方法所需步骤分配调用，但总预算一致。另可增加“各方法默认设置”的生态有效性分析，单独呈现，不能与同预算主比较混算。
- 固定 Maven/JDK、依赖缓存策略、测试运行超时、最大修复轮数和停止条件。建议使用干净依赖缓存或预热缓存的统一方案，避免某组承担首次下载成本。
- 预算协议、提示词和失败处理在读取正式结果前冻结；所有组采用同样的随机重复次数和随机种子记录规则。pilot 数据不计入正式统计。

### 主要指标

1. **分支覆盖率**：主要结果指标；同时报告行覆盖率。覆盖率基于最终通过的测试套件重新执行后生成的 JaCoCo 报告，明确分母和缺失覆盖报告的处理方式。
2. **测试有效性**：编译成功率、最终测试通过率、有效测试数量，以及从首次生成到最终有效套件的修复轮数。分别报告首轮和最终结果，避免只呈现修复后的最佳值。
3. **成本**：总 prompt/completion tokens、模型请求数、墙钟时间；若 LiteLLM 不提供可信费用，报告 token 和请求数，不推算费用。
4. **测试质量**：在可运行的子集上测量 mutation score；说明变异工具、版本、mutant 排除规则、有效 mutant 分母和运行预算。覆盖率不能替代该指标。
5. **稳定性**：对每种方法报告重复运行分布，包括均值/标准差及中位数/四分位距。可按方法做配对比较，并报告差值区间和效应量；统计单位以目标方法为配对单位，不能把同一方法内多个测试当成独立样本。

## 分析计划

- 首先回答分支覆盖率差异及其不确定性，再结合编译/通过率判断覆盖提升是否由可用测试带来。
- 绘制覆盖率随 token 或时间变化的曲线，并报告固定预算终点。该结果可展示 CogPath + OpenHands 是更快触达覆盖平台，还是仅靠更多交互取得更高最终值。
- 对每个方法汇总失败类型：编译错误、断言失败、目标路径不可达、依赖/fixture 缺失、超时、工具或环境错误。人工抽样审查生成测试的断言是否只复述当前程序行为。
- 对 CogPath + OpenHands 做轨迹分析：记录 agent 请求了哪些分析证据、是否使用、是否基于测试反馈改变策略，以及证据使用与覆盖增益之间的关系。
- 若无显著差异或 agent 组表现较差，如实报告；通过案例分析讨论哪些代码结构、路径条件或项目依赖导致差异。

## 当前可行性与前置问题

1. **Panta 尚不能作为本仓库内的可复现组。** 当前记录显示 Panta 在仓库外运行，仓库只保留派生 CSV。正式 RQ1 前需要找回官方/实验实现、精确模型和提示配置、数据版本、原始结果及预算；否则应将历史 CSV 作为背景结果而非本实验对照，或在论文中明确缩小比较范围。
2. **先修复会污染结果的 runner 问题。** 静态检查已发现 SymPrompt 测试结构嵌套问题、结束时可能删除配置指定测试文件，以及 CogPath 迭代异常仍可能返回成功状态。虽然 SymPrompt 不在当前四组中，其他共用验证/清理逻辑仍需先确认安全；所有正式运行应隔离副本并验证失败状态会被正确记录。
3. **HITS 的实验配置和实现需核对。** 确认切片排序/上限、是否包含失败测试修复、依赖上下文来源和完整 token 统计与方法定义一致。对实现作出的修正应记录为本地复现版本，不能笼统称为官方 HITS。
4. **四组不是天然可比。** CogPath + OpenHands 是带仓库工具操作的端到端工作流，Panta/HITS/CogPath 可能是固定生成-执行流程。公平的同预算比较可回答“同一资源下哪个可执行方案效果更好”，但不能直接证明 agent 架构单独导致提升；OpenHands vanilla 组可帮助分离这一因果因素。
5. **此前单案例运行只作为工程先导。** `JacksonXml-5f::ToXmlGenerator` 和 `Csv-16f::CSVParser` 上已有一次性运行记录，预算、迭代和修复策略不一致，且 CSVParser CogPath 有失败测试。它们可用于完善 runner，不能作为 RQ1 的正式统计证据。

## 当前结论边界

RQ1 的主张应定位为：**评估程序分析指导与工具使用 agent 组合后的测试生成效果、有效性和成本。** 在补齐 Panta 可复现实验、解决数据完整性问题、执行同预算重复实验并完成适当统计之前，不应声称该 workflow 已优于现有方法，也不应把覆盖率提升解释为更强的缺陷检测能力。
