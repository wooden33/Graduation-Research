\section{Motivation}

Recent LLM-based unit test generation approaches, such as SymPrompt~\cite{ryan2024}, HITS~\cite{wang2024c}, and Panta~\cite{gu2025a} have significantly reduced the manual effort required for testing complex methods. However, even with path-aware prompting and iterative refinement, a substantial gap in branch coverage remains.

We argue that this limitation stems from a fundamental \emph{cognitive misalignment} between the information provided to the LLM and the information required to cover a target branch. Specifically, effective branch coverage requires (i) satisfying implicit execution constraints and (ii) focusing on the minimal relevant context. Existing approaches, however, expose raw method bodies and implicitly expect the model to solve both problems simultaneously, leading to systematic failures.
We characterize this misalignment along two complementary dimensions.

\textbf{Challenge 1: Underspecified Constraints (What to Satisfy).}
Branch reachability often depends on implicit object states established through inter-procedural interactions~\cite{baldoni2018}. These constraints are not explicitly represented in the input, forcing the LLM to infer them from incomplete information.

Consider the \texttt{addValue()} method from Apache Commons Math (Listing~\ref{lst:motivation-cs}). The target branch depends on the condition \texttt{meanImpl != mean}, which can only be satisfied if a prior method modifies the internal state:

\begin{lstlisting}[language=Java, label={lst:motivation-cs}, caption={Target branch with hidden cross-method dependency}]
public void addValue(double value) {
 ...
 if (meanImpl != mean) {   // target branch
  meanImpl.increment(value);
 }
}
\end{lstlisting}

When provided only with the method body, the LLM typically generates:

\begin{lstlisting}[language=Java, caption={LLM-generated test (constraint not satisfied)}]
SummaryStatistics stats = new SummaryStatistics();
stats.addValue(1.0);
\end{lstlisting}

Although the test is executable, it fails to cover the branch because the required object-state constraint is never established. The correct test must explicitly satisfy the hidden precondition:

\begin{lstlisting}[language=Java, caption={Correct test (constraint satisfied)}]
stats.setMeanImpl(new CustomMeanImpl());
stats.addValue(1.0);
\end{lstlisting}

This example illustrates a general failure mode: when constraints are encoded as cross-method state transitions, they remain invisible unless explicitly surfaced, making them unlikely to be satisfied during generation.

\textbf{Challenge 2: Misaligned Context (What to Attend To).}
Even when all necessary conditions are locally available, they are often embedded within large methods containing substantial irrelevant logic. Providing the full method body introduces noise that is not aligned with the coverage objective.

Consider the \texttt{collect()} method from JacksonDatabind, where the target branch is guarded by a conjunction of three conditions:

\begin{lstlisting}[language=Java, caption={Target branch with multi-variable condition}]
if (checkJavaLangObject && (_intr != null) && !methods.isEmpty()) { ... }
\end{lstlisting}

Each condition originates from a different part of the method body. The full method interleaves the initialization of \texttt{methods}, the resolution of \texttt{checkJavaLangObject}, and several loops and nested branches entirely unrelated to the target guard. When exposed to the complete implementation, the LLM fails to identify that \texttt{\_mixInResolver} is the critical dependency, and generates a test that leaves \texttt{checkJavaLangObject} permanently false:

\begin{lstlisting}[language=Java, caption={LLM-generated test (branch not covered)}]
Collector collector = new Collector(intr, null); // _mixInResolver is null
collector.collect(typeFactory, tc, mainType, superTypes, primaryMixIn);
// checkJavaLangObject remains false; target branch never reached
\end{lstlisting}

By contrast, applying coverage-driven backward slicing retains only the statements that bear data or control dependence on the target branch, and folds the rest into abstract pseudocode:

\begin{lstlisting}[language=Java, caption={Branch-relevant slice}]
Map<MemberKey,MethodBuilder> methods = new LinkedHashMap<>();
_addMemberMethods(tc, mainType.getRawClass(), methods, primaryMixIn);
for (...) { ... }  // superTypes iteration -- no dependence on target branch
boolean checkJavaLangObject = false;
if (_mixInResolver != null) {
  Class<?> mixin = _mixInResolver.findMixInClassFor(Object.class);
  if (mixin != null) {
    _addMethodMixIns(...);
    checkJavaLangObject = true;  // sole setter of guard variable
  }
}
if (checkJavaLangObject && (_intr != null) && !methods.isEmpty()) { ... }
\end{lstlisting}

This focused representation makes the three guard dependencies structurally visible: \texttt{checkJavaLangObject} requires a non-null mixin for \texttt{Object.class}, \texttt{\_intr} is a constructor-injected field, and \texttt{methods} is populated by \texttt{\_addMemberMethods}. The aligned context enables the LLM to correctly configure the resolver and construct a valid initialization sequence:

\begin{lstlisting}[language=Java, caption={LLM-generated test with aligned context}]
Collector collector = new Collector(intr, resolver);
// resolver returns non-null mixin -> checkJavaLangObject = true
// _addMemberMethods populates methods -> !methods.isEmpty()
collector.collect(typeFactory, tc, mainType, superTypes, primaryMixIn);
// target branch covered
\end{lstlisting}

This reflects a second failure mode: even when constraints are present in the source, they are not structurally aligned with the model's attention, making precise reasoning difficult.
