\section{Motivation}

Recent LLM-based unit test generation approaches, such as SymPrompt~\cite{ryan2024}, HITS~\cite{wang2024c}, Panta~\cite{gu2025a}, and JUnitGenie~\cite{liao2025}, have significantly reduced the manual effort required for testing complex methods. However, they still struggle when branch reachability depends on implicit object states or is obscured by irrelevant context. We identify two key challenges.

\textbf{Challenge 1: Invisible Cross-Method Preconditions.}
Existing approaches typically provide the full method body as input, assuming that branch conditions can be inferred locally. In practice, however, the conditions required to reach a target branch are often established \textit{outside} the method via prior state initialization~\cite{baldoni2018surveysymbolicexecutiontechniques}. 

Consider the \texttt{addValue()} method from Apache Commons Math (Listing~\ref{lst:motivation-cs}). The condition \texttt{meanImpl != mean} can only be satisfied if \texttt{setMeanImpl()} is invoked beforehand, a dependency absent from the method body. As a result, LLM-generated tests typically execute successfully but fail to cover the target branch:

\begin{lstlisting}[language=Java, caption={Target branch with cross-method precondition}, label={lst:motivation-cs}]
public void addValue(double value) {
    ...
    if (meanImpl != mean) {   // target branch
        meanImpl.increment(value);
    }
}
\end{lstlisting}

\begin{lstlisting}[language=Java, caption={LLM-generated test (branch not covered)}]
SummaryStatistics stats = new SummaryStatistics();
stats.addValue(1.0);
\end{lstlisting}

The correct test must explicitly establish the hidden precondition:

\begin{lstlisting}[language=Java, caption={Correct test (branch covered)}]
stats.setMeanImpl(new CustomMeanImpl());
stats.addValue(1.0);
\end{lstlisting}

\textbf{Challenge 2: Attention Dilution from Irrelevant Context.}
Even when branch conditions are locally visible, they are often embedded in large methods containing substantial unrelated logic. This dilutes the LLM’s attention and hinders precise reasoning.

Consider the \texttt{collect()} method from JacksonDatabind, where the target block is guarded by a conjunctive condition:

\begin{lstlisting}[language=Java, caption={Target branch with multi-variable condition}, label={lst:motivation-bs}]
if (flag && intr != null && !methods.isEmpty()) { ... }
\end{lstlisting}

Each sub-condition depends on a different part of the method (e.g., constructor initialization, mix-in resolution, and method collection). When provided with the full method body, the LLM must reason over numerous irrelevant statements, making it difficult to identify and satisfy these dependencies:

\begin{lstlisting}[language=Java, caption={LLM-generated test (branch missed)}]
collector.collect(...);  // guard conditions not satisfied
\end{lstlisting}

By contrast, backward slicing isolates only the statements relevant to the guard conditions:

\begin{lstlisting}[language=Java, caption={Slice focused on branch dependencies}]
intr != null;
flag = resolveMixIn(...);
methods = collectMethods(...);
if (flag && intr != null && !methods.isEmpty()) { ... }
\end{lstlisting}

This focused context enables the LLM to correctly construct inputs that satisfy all conditions:

\begin{lstlisting}[language=Java, caption={LLM-generated test with slicing}]
collector = new Collector(intr, resolver);
collector.collect(...);  // branch covered
\end{lstlisting}

\textbf{Our Approach.}
We address these challenges with \ourmethod{}, a constraint-guided context-reduction framework. \emph{Constraint-Hints} explicitly extract and encode path conditions to expose hidden cross-method preconditions, while \emph{coverage-driven backward slicing} removes irrelevant context and retains only branch-relevant dependencies. Together, these mechanisms reduce the reasoning burden on LLMs and enable effective coverage of complex branches.
