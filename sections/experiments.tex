\subsection{Experimental Setup}

Following prior work \cite{gu2025a}, we excluded projects that do not use Maven or rely on deprecated dependencies (i.e., Chart, Mockito, and Closure). Furthermore, we manually excluded outliers such as classes with extreme complexity ($CC > 40$) caused by massive switch-statement patterns and those with minimal explicit control flow due to deep inheritance.The statistics of our evaluation dataset are summarized in Table~\ref{tab:dataset};

\textbf{Evaluation Metrics.}
To evaluate the effectiveness of the generated unit tests, we primarily focus on code coverage, which is the standard metric in automated test generation research \cite{randoop, evosuite}. We report two specific metrics:
\begin{itemize}
\item \textbf{Line Coverage (LC):} The ratio of executable lines in the target class that are exercised by the generated test suite. It provides a baseline measure of how much of the implementation has been reached.
\item \textbf{Branch Coverage (BC):} The ratio of executed decision outcomes (e.g., the true and false paths of an \textit{if} statement) to the total number of possible branches. Given our focus on methods with high Cyclomatic Complexity ($CC > 10$), branch coverage is our primary metric, as it more accurately reflects the tool's ability to navigate complex logical structures and boundary conditions.
\end{itemize}
All coverage data in our experiments are collected using the JaCoCo library, ensuring consistent and reproducible measurements across all subjects and baselines.

\textbf{Research Questions.}
To evaluate the effectiveness and design of \ourmethod{}, we address the following three research questions:

\begin{itemize}
\item \textbf{RQ1: Effectiveness Comparison.} How does \ourmethod{} perform compared to state-of-the-art LLM-based test generation approaches in terms of line and branch coverage on complex, logic-heavy methods?
\item \textbf{RQ2: Contribution of Components.} What are the individual contributions of the Backward Slicing (BS) and Constraint Solver (CS) components to the overall performance of \ourmethod{}?
\item \textbf{RQ3: Model Generalizability.} Is \ourmethod{}'s effectiveness robust across different underlying Large Language Models, and how do their performances vary?
\end{itemize}

\textbf{Baselines.}
To evaluate the performance of \ourmethod{}, we compare it against three state-of-the-art (SOTA) LLM-based unit test generation frameworks. These baselines represent diverse paradigms in the field:
\xtz{only explain the method of baseline.}
\begin{itemize}
    \item \textbf{SymPrompt \cite{ryan2024}:} A prominent prompt-engineering approach that integrates symbolic execution concepts with LLMs. It utilizes path-oriented prompts to guide models in generating test inputs. We include SymPrompt to assess the effectiveness of \ourmethod{} against methods relying solely on structured prompting without external constraint solving.
    \item \textbf{HITS \cite{wang2024c}:} A high-performance framework emphasizing self-healing and iterative refinement. As a strong baseline for generating compilable and high-coverage tests, HITS allows us to evaluate \ourmethod{}'s capability in navigating complex logical branches where iterative feedback is critical.
    \item \textbf{Panta \cite{gu2025a}:} A SOTA tool that leverages advanced path analysis and context-aware prompting. Panta excels at capturing data dependencies within the Class Under Test (CUT). Comparing against Panta demonstrates the advantages of \ourmethod{}'s synergy between branch selection and logical constraint satisfaction.
\end{itemize}

Due to the absence of several critical components in the official HITS repository, we faithfully re-implemented its workflow by strictly following the prompt templates defined in the original paper and adhering to the procedural logic of the available open-source fragments. 

For a fair comparison, all baselines were configured using the same backbone model as \ourmethod{} in each experiment. Specifically, RQ1 adopts \textbf{Qwen3-Coder-30B} (hereafter \textbf{QC3-30B}) as the backbone, while RQ2 adopts \textbf{Qwen3-Coder-30B} (hereafter \textbf{QC3-30B}). The use of different models across RQs reflects the distinct focuses of each evaluation: RQ1 prioritizes generation quality with a larger model, whereas RQ2 isolates the contribution of individual components under a more controlled, cost-efficient setting. Furthermore, all methods were provided with identical CUT information and dependency contexts to ensure that performance differences are attributable to the frameworks themselves rather than external information.

\textbf{Contextual Information.}
To evaluate the inherent logic reasoning and code understanding capabilities of the models, we adopt a restricted context strategy for all test generation tasks. Specifically, for each method under test (MUT), the prompt only includes the source code of its declaring class and the names of the associated import packages. No additional project-level information, such as dependency class implementations or global configuration files, is provided. This setup ensures that the performance of \ourmethod{} and the baselines is assessed under a consistent and challenging information-constrained environment, reflecting a realistic scenario where cross-file dependencies may be complex or partially inaccessible.

\textbf{Configurations.}
Our experiments employ two backbone LLMs depending on the research question. For RQ1 (effectiveness) and RQ3 (generalizability), we use \textbf{Qwen3.5-397B-A17B} (\textbf{QW3.5-397B}), accessed via its official API. For RQ2 (ablation study), we adopt \textbf{Qwen3-Coder-30B} (\textbf{QC3-30B}), deployed locally on a server equipped with an NVIDIA H800 GPU ($80$\,GB); this lighter model is chosen for the ablation setting to enable a controlled, cost-efficient comparison across component variants. To assess model generalizability in RQ3, we additionally evaluate OpenAI's \textbf{GPT-5.4-Mini} (\textbf{GPT-5.1-Mini}) and DeepSeek's \textbf{DeepSeek-V3.1} (\textbf{DS-V3.1}) via their respective official APIs.

To ensure reproducibility and minimize stochastic variance, all models are
configured with a temperature of $0.2$ and top-$p$ of $1.0$.

To answer RQ1, we compare \ourmethod{} against three state-of-the-art LLM-based test generation frameworks---SymPrompt, HITS, and Panta---on 14 real-world Java projects from Defects4J (v2.0.1). The evaluation focuses on both \textbf{line coverage (LC)} and \textbf{branch coverage (BC)} of complex methods, with Cyclomatic Complexity $CC > 10$. Results are summarized in Table~\ref{tab:coverage}.

\subsubsection{Overall Performance}

As shown in Table~\ref{tab:coverage}, \ourmethod{} consistently achieves the \textbf{highest average LC and BC} across all projects. Specifically, it attains an average BC of \textbf{44.41\%}, outperforming SymPrompt (21.14\%), HITS (34.24\%), and Panta (32.32\%). This demonstrates that the combination of \textbf{backward slicing} and \textbf{constraint hints} allows \ourmethod{} to more effectively navigate complex control flows and satisfy cross-method preconditions, compared with baselines that rely solely on prompt engineering or CFG-based analysis.

The improvement over SymPrompt is particularly substantial (\textbf{+89.3\%}), reflecting the limitation of approaches that lack explicit program analysis. Gains over HITS and Panta are smaller yet consistent (\textbf{+16.9\%} and \textbf{+23.8\%}, respectively), confirming that \ourmethod{}’s enhancements provide \textbf{complementary benefits} beyond existing path enumeration or context-aware prompting techniques.

\subsubsection{Performance on High-Complexity Projects}

The advantages of \ourmethod{} are most pronounced on projects with high cyclomatic complexity and deeper inter-method dependencies. For example:  

\begin{itemize}
    \item \textbf{Gson} (CC$_{avg}$ = 23.25, highest in the benchmark): BC of 41.24\%, while SymPrompt reaches only 3.59\%, highlighting the difficulty of context-unaware methods in handling complex branching logic.
    \item \textbf{JacksonCore} (CC$_{avg}$ = 16.33): BC improves from 18.51\% (HITS) to 35.54\% (\ourmethod{}), a gain of \textbf{+17 pp}, demonstrating that backward slicing effectively isolates branch-relevant statements.
    \item \textbf{Jsoup} (CC$_{avg}$ = 14.13): BC rises from 17.36\% (HITS) to 52.55\% (\ourmethod{}), a \textbf{+36.4 pp improvement}, underscoring the impact of constraint hints in constructing necessary object states to reach target branches.
\end{itemize}

These results indicate that \ourmethod{} excels particularly in logic-heavy methods where complex object interactions and conditional dependencies are prevalent.

\subsubsection{Cases of Limited Improvement}

While \ourmethod{} achieves the best average performance, there are a few projects where it does not outperform all baselines. For instance, \textbf{Collections} shows HITS achieving higher BC (70.00\%) compared to \ourmethod{} (34.63\%), and \textbf{Compress} has similar trends. Manual inspection suggests that these projects contain a high proportion of branches governed by \textbf{simple value-range conditions} rather than complex cross-method states. In such cases, backward slicing occasionally removes auxiliary context that would otherwise help the LLM, slightly reducing coverage. This points to a potential area for refinement in \textbf{slice granularity selection}.

\subsubsection{Summary}

In summary, \ourmethod{} demonstrates \textbf{robust effectiveness} across 14 real-world projects, achieving significant gains over state-of-the-art baselines, particularly in \textbf{high-complexity and logic-intensive methods}. The combined use of backward slicing and constraint hints enables the LLM to reach branches that are otherwise inaccessible to prompt-only or context-limited approaches.

\begin{tcolorbox}[colback=gray!5, colframe=gray!100, title=Answer to RQ1]
\ourmethod{} outperforms all three baselines on average, achieving a BC of \textbf{44.41\%}, representing improvements of \textbf{16.9\%--89.3\%} over SymPrompt, HITS, and Panta. Its advantage is most pronounced in projects with high cyclomatic complexity and cross-method dependencies (e.g., +36.4 pp on Jsoup, +17 pp on JacksonCore). In a minority of projects where branches depend primarily on simple value conditions, existing tools remain competitive, highlighting opportunities for further refinement in slice granularity.
\end{tcolorbox}

To evaluate the individual contributions of Backward Slicing (BS) and Constraint Hints (CS), we conducted an ablation study with three degraded variants: \textbf{w/o BS} (removing backward slicing), \textbf{w/o CS} (removing constraint hints), and \textbf{w/o CS+BS} (removing both). All variants share the same iterative generation loop and are evaluated under an identical backbone (QC3-30B). Results are summarized in Table~\ref{tab:ablation}.

\subsubsection{Overall Ablation Results}

\textbf{Both components contribute independently.} Removing BS alone causes an average BC drop of \textbf{5.94 percentage points} (44.41\% $\to$ 38.47\%), while removing CS alone results in a drop of \textbf{4.62 pp} (44.41\% $\to$ 39.79\%). Removing both components yields the largest degradation of \textbf{7.84 pp} (44.41\% $\to$ 36.57\%), confirming that BS and CS address complementary aspects of the problem: BS eliminates irrelevant context that misleads the LLM, while CS makes cross-method preconditions explicit so that the LLM can construct the required object state. Notably, the combined degradation (7.84 pp) is smaller than the sum of individual degradations (10.56 pp), suggesting that the two components partially compensate for each other when one is absent.

\textbf{BS is particularly critical for context-heavy methods.} The impact of BS is most pronounced in projects where method bodies contain many statements unrelated to the target branch. On \textit{Csv}, removing BS causes BC to drop from 52.29\% to 24.80\% ($-$27.49 pp), the largest per-project degradation in the study. This aligns with our motivation: when irrelevant statements dominate the focal method, providing the full unsliced context actively distracts the LLM from the branch-relevant logic.

\textbf{CS is critical when preconditions span method boundaries.} CS contributes most on projects where the target branch condition depends on prior method calls. On \textit{JacksonDatabind}, removing CS reduces BC from 17.85\% to 9.33\% ($-$8.52 pp, a relative decline of 47.7\%), indicating that without explicit constraint hints the LLM is unable to construct the object state necessary to reach the focal branch.

\textbf{Anomalies and discussion.} In two projects (\textit{JacksonCore} and \textit{Jsoup}), the w/o-BS variant achieves marginally higher coverage than the full \ourmethod{}. We attribute this to cases where backward slicing inadvertently removes type information required for mock construction, causing the LLM to fall back on simpler yet occasionally effective test patterns. This sensitivity to slice granularity is a known limitation and remains a direction for future refinement.

In contrast, removing either component leads to slower convergence, and removing both produces the flattest growth trajectory, underscoring the necessity of each component for sustained progress.

Table~\ref{tab:model-generalization} presents line coverage (LC) and branch coverage (BC) achieved by each model across 14 real-world Java projects. Notably, QW3.5-397B and DS-V3.1 attain the highest average branch coverage (83.47\% and 80.12\%, respectively), indicating that larger and more advanced models tend to produce more semantically accurate and coverage-effective tests. In contrast, smaller models such as QC3-30B achieve lower coverage (44.41\%), highlighting the influence of model reasoning capacity on path exploration, particularly in projects with higher cyclomatic complexity.

Across all projects, \ourmethod{} demonstrates the ability to generate tests that traverse complex execution paths and satisfy intricate object state dependencies, which often remain uncovered by smaller or less capable LLMs. The performance gap is most pronounced in projects such as \texttt{Collections} and \texttt{JDatabind}, where intricate state initialization and cross-method interactions are critical for branch reachability. This suggests that model capacity plays a significant role in LLM-based test generation, especially when reasoning about implicit preconditions and multi-step object state construction.
