\section{Related Work}

\subsection{Automated Unit Test Generation}

Early techniques such as Randoop~\cite{randoop} and EvoSuite~\cite{evosuite} drive test generation by optimizing structural coverage objectives. EvoSuite applies evolutionary algorithms over whole test suites to maximize branch coverage and automatically infers regression assertions. While effective at exploring input spaces, SBST methods fundamentally operate on syntactic signals and struggle with semantic preconditions that require understanding object states or inter-procedural call sequences~\cite{mcminn2011}.

Neural sequence-to-sequence models offered a first bridge between code understanding and test synthesis. ATLAS~\cite{watson2020atalas} frames test generation as a translation task, training an encoder--decoder network to predict assert statements from focal methods. AthenaTest~\cite{Tufano2020UnitTC} extends this direction by fine-tuning pre-trained models on large method--test corpora to automate full JUnit test synthesis. These deep learning approaches demonstrate that neural models can capture surface-level code patterns, but their capacity is fundamentally bounded by the training distribution: they cannot reliably generalize to the combinatorial space of runtime behaviors or reason about execution semantics~\cite{allamanis2018ml4code}.

The advent of large language models enables open-ended test synthesis grounded in broad code understanding. Early work such as ChatUniTest~\cite{chen2024}, CodaMosa~\cite{lemieux2023codamosa} demonstrates the potential of LLM-based generation, but also exposes a key limitation: without structured guidance, models tend to produce superficially plausible tests that fail to reach complex branches.

A first wave of follow-up work addresses this gap by incorporating execution signals into the generation loop. CoverUp~\cite{pizzorno2025} iteratively targets untested code regions using dynamic coverage reports, directing the model's attention toward uncovered lines, while YATE~\cite{konstantinou2025yate} further repairs failing tests to improve validity. FailMapper~\cite{dong2025failmapper} integrates a Failure-Aware Monte Carlo Tree Search algorithm~\cite{xie2024montecarlotreesearch} with LLMs to intelligently explore test inputs targeting these failure scenarios.

A second wave enriches the model's input with structural program information. SymPrompt~\cite{ryan2024} extracts branch conditions from control flow graphs (CFGs) and embeds them as structured prompts. HITS~\cite{wang2024c} decomposes complex methods into smaller slices to reduce cognitive load, improving syntactic validity. Panta~\cite{gu2025a} combines static CFG analysis with dynamic coverage feedback to identify and target uncovered paths. JUnitGenie~\cite{liao2025} further achieves strict path sensitivity by constructing minimal, path-specific contexts using type and data-dependency information. PALM~\cite{chu2025palm} similarly embeds intra-procedural branch conditions extracted from the method-level CFG into path-specific prompts, but does not address the inter-procedural object-state dependencies that Constraint-Hints is designed to surface. LSPRag~\cite{GoLSPRAG2026icse} leverages language server protocols to retrieve cross-file dependency context, augmenting the model's view beyond the focal method. These advances substantially reduce the structural mismatch between model input and the coverage objective. However, a key limitation remains: branches whose reachability depends on cross-method object states-preconditions established by prior setter or initializer calls—are still difficult to capture, as such dependencies are not explicit in the focal method. In addition, even with path-level guidance, irrelevant statements in the full method context introduce substantial noise, degrading model effectiveness as complexity grows~\cite{du2025contextlengthhurtsllm,wang2026intelligencedegradationlongcontextllms}. Our work targets these limitations by making implicit preconditions explicit and focusing the model on branch-relevant dependencies.

\subsection{Program Slicing}

Program slicing~\cite{weiser1984,tip1995} extracts the subset of statements that influence a particular variable or program point. Classical static slicers identify data and control dependencies via program dependence graphs~\cite{ferrante1987}; JavaSlicer~\cite{JavaSlicer} extends this to Java programs by constructing precise inter-procedural dependence graphs over bytecode. These techniques have been widely applied in debugging, program comprehension, and regression testing. However, classical static slicers require complete, parsable code: tools such as Joern fail on incomplete snippets due to missing type declarations, unresolved imports, and references to external libraries. NSSlicer~\cite{yadavally2024} addresses this limitation by leveraging a pre-trained language model to learn fine-grained variable--statement dependency patterns, enabling slicing of both complete and partial Java programs where traditional analysis is brittle.

More recently, Shahandashti et al.~\cite{shahandashti2024programslicingeralarge} demonstrate that LLMs can perform program slicing directly from source code without dedicated analysis infrastructure, achieving results competitive with specialized neural slicing tools. In particular, GPT-4o under one-shot with chain-of-thought prompting reaches an Accuracy-D of 60.84\%, slightly surpassing NS-Slicer (CodeBERT~\cite{feng2020codebert}) at 60.52\%, while also generating exact matches that NS-Slicer entirely fails to produce.

HITS~\cite{wang2024c} applies a form of method decomposition to reduce LLM input complexity. However, its decomposition is driven by structural heuristics rather than data and control dependencies, and is not targeted toward any specific uncovered branch. For high-complexity methods, the number of generated segments can grow substantially, incurring token overhead regardless of coverage impact.

In contrast, \ourmethod{} performs coverage-driven backward slicing: it starts from a specific uncovered branch, traces its data and control dependencies—including cross-method field initializations—and produces a minimal, branch-specific context. Unlike HITS's structural decomposition, our slicing is triggered only when coverage stalls and targets exactly the dependencies needed to cover a given branch.
