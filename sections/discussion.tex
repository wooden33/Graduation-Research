\section{DISCUSSION}

\textbf{Cost and Token Efficiency.} 
\ourmethod{} introduces additional prompting overhead due to backward slicing and constraint hint construction. 
Across all 3,576 requests, the total token consumption amounts to \textbf{221.8 million input tokens} and \textbf{6.1 million output tokens}. 
However, a substantial portion of the input tokens (\textbf{181.5 million}) are served from cache due to repeated prompt structures, leaving only \textbf{40.3 million tokens} billed.

Using GPT-5.4-mini pricing, the total cost of our experiments is approximately \textbf{\$58}. 
For a typical project with around 130 focal methods, this corresponds to a cost of approximately \textbf{\$2 per project}, demonstrating that \ourmethod{} is cost-effective for practical deployment.

The backward slicing step further improves efficiency by reducing prompt length by approximately \textbf{25\%}, ensuring that tokens are primarily allocated to semantically relevant context. 
Together, slicing and caching significantly improve the coverage-per-token ratio compared to naive full-context prompting.

\textbf{Qualitative Insight.} 
To understand the source of performance gains, we examine a representative example from the \textit{Favicon for Alibaba} project. 
The method \texttt{generateFavicon} contains a branch condition \texttt{if (icon != null \&\& icon.size() > 0)}, which requires proper object initialization prior to invocation. 
Baseline approaches typically invoke the focal method directly, failing to satisfy the implicit precondition and leaving the branch uncovered. 

In contrast, \ourmethod{} applies backward slicing to identify the relevant state-modifying call \texttt{setIconState}, and provides an explicit constraint hint describing the required precondition. 
The generated test consequently initializes the object correctly and triggers the target branch. 
This example highlights that \ourmethod{} improves not only coverage, but also the LLM’s ability to reason about cross-method dependencies and implicit state requirements.

\textbf{Differentiation from Existing Approaches.}
Several recent works incorporate program analysis or iterative feedback into LLM-based test generation, and \ourmethod{} shares surface-level similarities with some of them.
We therefore clarify below precisely how \ourmethod{} differs from each line of prior work on the two dimensions that define its design: \emph{what to satisfy} and \emph{what to attend to}.

\textit{Versus HITS.}
HITS decomposes the focal method into smaller fragments to reduce LLM input size.
However, its decomposition is driven by structural heuristics rather than data or control dependencies, and is applied uniformly regardless of the current coverage state.
As a result, the fragments are not targeted at any specific uncovered branch, and for methods with high cyclomatic complexity the number of generated segments grows proportionally, incurring substantial token overhead even for already-covered regions.
\ourmethod{} instead performs \emph{coverage-driven} backward slicing: the slicer is triggered only when coverage improvement stalls, and each slice is computed starting from the precise uncovered branch condition, tracing all data and control dependencies—including cross-method field initializations and setter definitions—that govern its reachability.
This guarantees that every slice is both necessary and precisely targeted at the branch that resists generation.

\textit{Versus SymPrompt.}
SymPrompt extracts branch conditions from Control Flow Graphs and embeds them as structured prompts.
Yet constraint inference and test synthesis remain compressed into a single LLM call: the model must simultaneously determine what conditions must hold \emph{and} write code that satisfies them, with no intermediate verification of the inferred constraints.
This leaves the model free to silently skip or misinterpret complex dependency chains.
\ourmethod{} explicitly decouples these two tasks: a dedicated Constraint-Hints step first derives the reachability conditions as interpretable statements and surfaces them to the generation prompt; only then does the test generation LLM synthesize code.
This staged design eliminates the single-step reasoning bottleneck that causes SymPrompt to fail on branches with long or non-local dependency chains.

\textit{Versus Panta.}
Panta fuses static CFG analysis with dynamic coverage feedback to identify and prioritize uncovered paths, then passes the path information to the LLM for test generation.
Like SymPrompt, however, Panta's path specification is fed into a unified generation step that conflates constraint reasoning with code synthesis.
Moreover, Panta's path analysis operates strictly within the focal method body, leaving cross-method object-state dependencies invisible: if the condition required to reach a target branch can only be established by calling a setter defined in a different method, Panta has no mechanism to surface that dependency.
\ourmethod{} addresses both gaps: Constraint-Hints explicitly models inter-procedural preconditions, and backward slicing traces dependencies across method boundaries to bring the necessary setter and initializer context into scope.

\textit{Versus JUnitGenie.}
JUnitGenie achieves strict path sensitivity by constructing minimal, path-specific contexts using type and data-dependency analysis within the focal method.
This directly addresses the attention dilution problem on the \emph{what to attend to} dimension.
However, JUnitGenie's context minimization is bounded by the focal method boundary: cross-method state-setting operations that must be invoked \emph{before} the method under test remain invisible.
\ourmethod{}'s backward slicing explicitly extends dependency tracing beyond this boundary, incorporating setter calls, field initializers, and dependency class implementations from related classes into the sliced context.
Furthermore, \ourmethod{} complements context reduction with the Constraint-Hints mechanism, which addresses the orthogonal \emph{what to satisfy} dimension by making implicit cross-method preconditions actionable—a gap that JUnitGenie does not target.
}

\textbf{Design Implications.}
Our findings suggest that structural guidance (e.g., slicing and constraint hints) and model reasoning capabilities are complementary. 
While \ourmethod{} effectively reduces irrelevant context and exposes execution constraints, its full potential is realized when paired with LLMs capable of multi-step reasoning and semantic inference. 
This indicates that future improvements in LLM reasoning ability can further amplify the effectiveness of structured test generation frameworks.

\textbf{Limitations.} 
Despite its effectiveness, \ourmethod{} has several limitations. 
\emph{Slice granularity.} For projects such as \textit{Collections} and \textit{Compress}, where branch conditions depend primarily on value ranges rather than cross-method state, backward slicing may remove useful auxiliary information (e.g., boundary constraints), potentially reducing test quality. Conversely, overly coarse slices may introduce irrelevant context. Designing adaptive slicing strategies remains an important direction for future work. 

\emph{Scalability.} Backward slicing and constraint extraction introduce preprocessing overhead proportional to the inter-procedural dependency graph. In our evaluation, the average preprocessing time per focal method is \textbf{1.2\,s}, which is acceptable for medium-scale projects. However, further optimizations such as incremental or on-demand slicing may be required for large-scale industrial systems.
